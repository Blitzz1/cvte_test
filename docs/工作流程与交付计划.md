# AVQualityMonitor 工作流程与交付计划

> 状态：需求基线、流程和可行性报告v0.1已编写；环境准备与业务开发尚未开始。
> 日期：2026-10-26；全部时点使用北京时间。
> 需求依据：[需求与验收基线](./需求与验收基线.md)。需求编号用于检查覆盖情况。

## 1. 工作顺序与完成原则

总体顺序：

**需求基线 → 可行性报告初版与风险清单 → 环境与关键能力验证 → 回填选型结论 → 核心设计初版 → 最小真实测量链路 → 分模块实现与同步文档测试 → 基础完整验收 → 加分扩展 → 稳定性与离线演练 → 最终交付。**

1. 先说明如何取得可信原始数据、如何测量，再实现和展示指标。
2. 可行性报告先于业务功能代码。先依据官方资料确定推荐方案并形成初版，再按风险清单开展小型实验、回填结论；实验不直接当成完成产品。当前初版见[可行性分析报告](./可行性分析报告.md)，所有实验状态仍为待验证。
3. 核心设计初版先于核心业务代码，尤其是观测点、时钟、归因、软件呈现语义和并发生命周期。
4. 每个模块先补齐对应设计，再实现、测试，随即回填文档与需求追踪；不等代码全部完成才补文档。
5. 核心单元测试与算法实现同阶段完成，三类异常的集成复现从最小链路阶段开始准备。
6. 基础要求通过后扩展加分项；加分项影响公共链路时，重新验证受影响的基础功能。
7. 只有真实执行且留有证据的测试才能写“通过”；计划、未执行、失败、受限须区分。
8. 该流程不自动启动下载、安装、长测或开发；在用户指示开展后续工作时执行。

## 3. 阶段0：保存基线、建立版本控制

### 工作

- 检查已有目录、仓库和适用约定，保留现有文件。
- 当前目录初始为空，最初未找到Git；用户安装后，已通过完整路径验证Git可用并初始化仓库。后续检查PATH是否刷新，无需重复安装或初始化。
- 检查Git作者配置，不猜测用户姓名或邮箱；缺失时按实际需要向用户索取。
- 将需求基线、工作流程及可行性报告v0.1一并作为首次文档提交，记录其实际创建背景，不补造日期或历史。
- 建立合适的忽略规则，避免纳入构建产物、依赖缓存、大录像、数据库、日志、密钥等。

### 阶段出口

- 可查看Git状态及提交历史；需求与流程均可追踪。
- 没有把依赖缺失或初始化失败写成已完成。

## 4. 阶段1：环境调查与可行性分析，先形成报告

### 先调查，再选型

1. 记录实际Windows版本、编译器、CMake、SDK、Git、磁盘空间和浏览器环境。
2. 调查候选协议／编解码库、本机媒体服务器、Web与存储组件的官方资料、Windows可用性、许可及离线分发要求。
3. 对每个候选组件明确原始数据能力：包序号、RTP时间与RTCP、压缩帧边界、PTS／DTS、解码输出、采样位置、调度／呈现观测等。
4. 验证RTSP推拉、UDP／TCP、RTMP推拉、H.264／AAC是否真正可组合；不能把库声称支持协议当成本项目实际路径已验证。
5. 优先做最小关键实验：可信源端参考能否穿过链路、如何匹配接收帧、软件呈现观测如何取得、音频时间基准如何统一、丢帧归因证据是否足够。
6. 检查时钟及软件呈现的能力边界，明确测量误差验证方法；不能通过重命名解码完成或预定播放时刻规避呈现要求。
7. 初步检查CPU／GPU方案、4路资源预算、8路风险及录像容量策略；实际性能结论留给后续实测。

### 必须先写的文档

- 完成独立《可行性分析报告》：选择理由、候选比较、原始数据层级、自研边界、关键实验事实、风险措施、环境要求及开发计划。
- 建立《依赖与运行环境》：确定版本、下载来源、准备方式和离线需求。依赖在演示前全部准备完成。
- 报告不写未经验证的肯定结论；不可行路径必须先调整方案，涉及已确认范围变化时再与用户确认。

### 阶段出口

可行性报告已形成并纳入Git；核心观测路径具有可执行方案，关键疑点有实验结果或明确待验证项。到此才进入业务实现。

## 5. 阶段2：先写核心设计和测试计划，再搭建骨架

### 代码前必须明确

- 模块与数据流：源端、推流、媒体服务、拉流、解码、软件播放观测、检测器、告警、持久化、API与网页。
- 每路生命周期、线程／任务模型、队列与背压、断连和重连、资源释放、异常隔离。
- 核心接口和数据结构：流ID、帧ID、会话ID、时间基准、原始观测、有效性、归因、指标样本、告警事件。
- 三类指标公式、正负方向、统计分母与窗口、刷新、预热、时钟映射和误差。
- RTSP UDP、RTSP TCP与RTMP的证据差异；RTP包损失到帧缺失的判定；可靠传输不能凭空产出网络帧丢失。
- 源端标记、源／收／呈现记录如何关联，以及普通外部流降级为不可测或不可判定的规则。
- 软件呈现观测语义：4路都运行独立观测，网页预览与主测量边界分开；无真实上屏时清楚表述。
- 配置文件与网页设置的一致性、即时生效范围、需重启任务的参数、持久化数据模型、清理和媒体容量上限。
- 告警状态机：多级阈值、防抖、恢复、重试，数据缺失和不适用的处理。
- 测试真值、异常注入位置、可测误差及证据收集方式。

### 同阶段输出

1. 《设计文档》核心初版。
2. 《测试计划与记录》中的用例计划，包含三类异常、归因、4路与1小时稳定性。
3. 《需求验收追踪》初表，所有基础需求都有计划证据。
4. 随后建立CMake骨架、模块目录、测试入口和README；验证最小构建与启动。

### 阶段出口

核心设计可用于实现；没有“实现后再决定测什么”的指标；项目骨架可构建，文档版本已提交。

## 6. 阶段3：最小真实测量链路与自研核心

### 推荐顺序

1. 可控源与本机媒体服务，先贯通单路实际推拉、解码和软件播放观测。
2. 保存可信源端时间／帧标记，接收与呈现观测能够对应到同一帧。
3. 实现端到端延迟，使用可核对的时间记录验证，说明误差与无效样本。
4. 实现音画偏差及时间基换算，再实现漂移趋势；验证正负方向、固定错位与渐进漂移。
5. 实现丢帧计数、分母、连续丢帧与分层归因；实现冻结与会话边界。
6. 为RTSP／RTMP和UDP／TCP补齐差异路径；同时准备三类异常的可重复注入。
7. 加入普通外部流能力状态，确保不可测值不被记为正常数值。

### 文档与测试同步规则

- 每实现一种指标，更新其公式、观测位置、单位、窗口、阈值与限制。
- 核心单元测试覆盖真值、边界、乱序／迟到／重复、断连重连和时间异常等适用情况，不用仅复述实现的测试充数。
- 异常注入必须经过真实检测路径，记录注入值、实测值、误差与预期告警，不以修改显示数据替代。
- 每个完成的测量闭环形成可追踪提交，并回填需求编号。

### 阶段出口

三类主指标有可信输入、自研计算和验证证据；已能解释各路径的能力限制。未满足的测量核心问题优先解决，不先堆叠界面功能。

## 7. 阶段4：基础功能集成，持续补全设计与使用说明

### 实现内容

- 独立流任务、配置、状态查询、重连与隔离；达到4路拉流检测并同时执行两种协议推流。
- 指标及事件持久化、历史固定范围与自定义时间、保留与清理策略、可配置日志。
- 阈值／防抖／恢复状态机、Webhook通知和本地接收演示。
- 网页总览、单路详情与三张近5分钟趋势图、可切换预览、历史与事件查询。
- 网页常用配置与配置文件持久化；显示需重连、生效失败、无效或不可测状态。
- 统一启动管理本机依赖，提供就绪检查、失败信息和正常退出；页面正常使用不依赖联网资源。

### 同步文档

- 实际接口、配置格式、数据库、页面数据语义发生变化时同步《设计文档》。
- 将已验证的命令与配置例子写进README，不能只保留计划命令。
- 补充《现场演示指南》初版；按需求追踪表逐项补测试证据。

### 阶段出口

基础功能全部可用；三类异常从注入、检测、告警、通知、存储到历史回查形成闭环；本机4路场景已有验证。

## 8. 阶段5：基础验收后推进加分项

初始建议：同步交叉验证、宫格预览、HTTP-FLV较早争取；再根据负载和关键实验推进8路、离线复盘、推流观测、时钟分析与WebRTC。

每项加分遵循：**先补设计与测试标准 → 实现 → 针对性验证 → 更新说明和追踪表 → 提交Git**。

- 第二种同步验证要具有独立性，不能只是同一公式换一种展示。
- 8路须实际运行验证，不能只把配置上限改为8。
- 离线复盘同时保留必要观测记录；录像不足以恢复的事实不得宣称可重建。
- 时钟与单向延迟估计须说明假设，不能替换主延迟实测。
- 推流观测明确本地证据与接收端反馈边界。
- HTTP-FLV／WebRTC要纳入检测闭环，不能只实现播放就标完成。

时限不足时记录未完成项，停止增加高风险范围，优先保证基础正确、文档和演示完整。若加分项改变公共代码，补做受影响的回归测试。

## 9. 阶段6：稳定性、离线演练与交付冻结

### 必做验证

1. 基础验收组合连续运行1小时，记录流配置、推流任务、CPU／内存、错误、指标趋势、连接事件与测量有效性。
2. 检查内存增长与资源释放，必要时结合诊断工具；准确描述证据能支持的结论。
3. 验证单路断开／重连、隔离、会话重置和历史保留；验证短时异常不会被防抖抹去。
4. 检查依赖完整、静态页面资源本地化、离线统一启动和停止、端口冲突及失败提示。
5. Chrome主演示路径与Edge兼容验证；用实际操作复核预览切换、历史、自定义时间和网页设置。
6. 排演三类异常、Webhook、归因与恢复，再次确认现场状态不是伪造或遗留测试数据。

### 最终文档工作

- 可行性报告更新为最终选型事实，保留必要决策说明。
- 设计文档与实际实现一致，指标口径和限制完整。
- 测试记录区分通过／失败／未执行，附环境、时间、版本和证据路径。
- 需求追踪表检查全部基础项，加分项单独报告。
- README与现场演示指南用最终版本实际复现。
- 记录已知限制、依赖清单及复现方法，提交最终验收材料。

长测后若修改影响测量、资源、并发或生命周期的代码，需重测受影响范围；不能继续引用旧版本长测结果为新版本背书。

## 11. Git提交与日常推进规则

- 开始每个工作段前检查工作区，避免覆盖用户或其他已有修改。
- 一个提交表达一个清楚目的：需求、设计、功能、修复、测试或使用说明；紧密相关的代码与文档可在同一提交。
- 示例主题：`docs: 明确指标观测与验收口径`、`feat: 实现帧级延迟测量`、`test: 验证RTSP乱序与帧归因`。这些只是主题示例，不得预先创建空提交冒充进展。
- 提交前查看差异，执行与该变更相称的检查，避免混入依赖产物、秘密或无关文件。
- 保留真实提交时间与历史；不为制造“完整历史”拆分虚假里程碑，不改写已完成历史伪造开发过程。
- 每阶段说明已完成、证据、剩余问题与下一步；不将未验证功能报告为完成。
- 原文要求每周至少一次进度同步；本项目只有四天，按阶段及时同步，有问题及时沟通，无需另设自动通知。
- 需求口径变化先更新基线；普通实现细节自行合理决定，遇到影响验收范围、可信测量或截止时间的关键问题及时说明。
