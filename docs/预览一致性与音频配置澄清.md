# 预览一致性与音频配置澄清

> 最新预览实现（2026-10-28）：默认及宫格已复用同路WIC实际输出的按需JPEG镜像（最多10张／秒），不新增服务器拉流；HLS仅为显式原流对照。本机音频仍走实际WASAPI消费，网页图像有额外展示延迟。此前待补说明为历史阶段，当前证据见[检测输出预览验收记录](./检测输出预览验收记录.md)。

> 2026-10-28。回应用户对配置入口和监控预览意义的疑问；本轮未实现新的媒体输出传输，也未改变检测终点。

## 范围调整

用户明确取消B-03推流侧独立质量观测，不作为基础或加分交付，不再列入未完成项。其余7项加分保留原编号；源端推流、帧身份与释放时间等原始记录仍是完整链路检测的必要部分。

## has_audio在哪里改

网页“运行配置”目前是完整JSON编辑器，没有独立的音频开关。has_audio可选，未写默认true，所以可能找不到现成字段。需要在chains数组对应链路对象内添加，不能把下述片段替换成整个配置：

```json
"source": "data/media/sample-1080p30-no-audio.mp4",
"has_audio": false
```

注意与相邻字段之间的JSON逗号，点击校验并保存，再选择该路重启。若有音轨则设true或省略。网页已补入口说明，素材替换指南也同步；用户现有config/app.json保持不动。

## 当前预览确实存在一致性缺口

当前主检测：服务器→RTSP／RTMP拉流→解码→WIC软件画面输出／WASAPI音频消费。当前网页预览：服务器→HLS→浏览器，是另一条接收播放路径。它可以确认原流有画面，但不能展示本程序接收后丢帧、呈现丢帧或播放调度异常；也不测量该浏览器实例的实际声画同步。

若监控预览的目标是“查看被检测端实际输出”，当前原流预览不充分。此前将能播放HLS等同基础预览全部完成的表述应收紧，不能仅靠解释两个路径不同就认为一致性问题已解决。

建议的后续设计是把检测端实际输出作为主预览，HLS原流仅保留为可选对照。视频应从完成WIC输出后的真实画面取得，不能重新拉服务器原流冒充镜像；可以复用原有解码和输出事实，无需增加第二条服务器拉流。向浏览器传递镜像图像仍产生本机编码／传输和显示开销，这部分延迟需另行说明，不改变主检测的WIC终点。

若主预览还要求听到与检测输出一致的音频，须同时设计音频镜像、统一时间关系及浏览器缓冲，不能仅给视频截图配一条独立原流音频就宣称一致。具体浏览器输出格式、音频处理和资源预算尚未固化或实现，本轮不把方案当交付结果。

服务器当前hlsAlwaysRemux=yes，即使浏览器未预览也会生成HLS。后续若原流仅作可选对照，可评估按需生成，避免额外后台开销；此项本轮没有修改。
