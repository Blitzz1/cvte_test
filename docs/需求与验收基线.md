## 1. 使用约定与范围

- 原始项目名称：音视频质量监测系统（简化版），AVQualityMonitor。
- 核心目标：准确、可验证地测量端到端延迟、音画同步、视频丢帧，并能解释检测口径和异常原因。
- 质量检测仅围绕上述三类，不主动增加清晰度、噪声、MOS 等其他质量维度。
- 优先完成全部基础要求，尽可能完成全部加分项；困难加分项可以后置。
- 用户明确约定优先于截图中的一般性表述。技术选择或验收范围发生变化时，应记录原因并同步本文、设计与测试。
- 复选框只在完成实现且取得相应验证证据后勾选。文档写完、接口存在或界面有数字，不等于对应功能验收通过。
- 技术参数中标为“初值”的内容已获用户接受，但需经过实测校准，并记录调整依据。

## 4. 流接入、推送与并发

### 4.1 基础范围

- [ ] F-01 RTSP 1.0、RTMP 均支持推流与拉流；RTSP 同时覆盖 RTP over UDP 与 RTP over TCP。
- [ ] F-02 基础编码范围为 H.264 视频与 AAC 音频；其他编码不是已承诺的基础要求。
- [ ] F-03 同一程序具备本地媒体推送到目标服务，以及从目标地址拉取媒体并检测的能力。程序本身不要求充当媒体服务器；可使用由统一启动入口管理的本机第三方媒体服务器。
- [ ] F-04 推流源、拉流地址、推流目标、协议、推拉方向、别名、是否有音频等可配置，增加或修改流不依赖修改代码。
- [ ] F-05 必须支持本地文件及程序生成的可控音视频测试源；真实摄像头和麦克风采集属于可选功能，验收不依赖购买或使用这些设备。
- [ ] F-06 每路独立管理连接、断开、重连；单路异常不能影响其他流。
- [ ] F-07 提供连接状态、当前码率、分辨率、帧率、音频采样率、已运行时长等信息。

### 4.2 已确认的较充分并发验收

- [ ] F-08 同时拉取并检测4路独立流：RTSP 2路、RTMP 2路，每路1080p30且含音频；同时保持RTSP、RTMP推流任务运行。
- [ ] F-09 不用“2个推流任务＋2个拉流任务”冒充4路同时检测。相同素材可以复用，但检测流须有不同地址、独立生命周期和独立指标。
- [ ] F-10 验证RTSP的UDP与TCP路径，记录实际使用的混合组合；4路基础与8路加分均需注明并发范围、推流任务数量及配置。

基础推流要求是完成推送业务；三类指标的完整基础检测主要在拉流侧完成。推流侧质量观测属于加分项，发送成功不代表远端已实际呈现。

## 5. 测量共同原则

- [ ] M-01 每项指标文档明确四项：观测位置、计算窗口与刷新周期、单位、阈值及依据。
- [ ] M-02 明确各时间值来自哪种时钟、时间基准如何统一、音视频时间基不同时如何换算，以及重连、时间戳回绕和跳变的处理。
- [ ] M-03 主验收使用可控测试流，保留可信源端时间、帧编号、同步参考标记及必要观测记录，用实际链路和已知异常验证计算结果。
- [ ] M-04 普通外部RTSP／RTMP流仍支持接入和可用指标检测；缺少可信参考的指标显示“不可测”或“不可判定”，说明证据、缺失信息和限制，不显示伪造数值或当作零。
- [ ] M-05 可控流应实际证明传输丢失与呈现丢弃的区分，不能以全部“不可判定”替代归因实现。
- [ ] M-06 使用明确记录的软件播放呈现观测点作为主测量终点，浏览器负责看板与预览；基础测量不要求涵盖浏览器额外预览缓冲、显示器实际发光或扬声器实际发声。
- [ ] M-07 每路持续运行软件播放调度观测环节，即便当前没有在网页预览；未上屏流必须标明软件观测位置，不将“解码完成”或预定调度时刻冒充实际呈现。观测能力与误差需设计、验证并记录。
- [ ] M-08 对无音频流，音画同步应显示不适用，不能捏造正常状态；基础并发验收仍使用含音频流。

## 6. 三类核心指标

### 6.1 端到端延迟

- [ ] L-01 测量源端采集到监测端可观测呈现之间的总延迟，单位毫秒；须有可验证的实测依据，不接受仅估算或推算的结果充当主指标。
- [ ] L-02 本地文件模拟采集时，以每帧按实时节奏进入源端处理链路的时刻为源端参考时刻，并明确其不是真实摄像头采集。
- [ ] L-03 原始媒体PTS不自动等于真实采集时刻，不能直接与当前墙钟相减作为端到端延迟。
- [ ] L-04 同机时钟可比较关系、跨时钟映射、参考标记传递和匹配、标记丢失及测量误差都需解释；允许误差须通过实际验证给出，当前未约定固定数值。

### 6.2 音画同步

- [ ] A-01 输出音画偏差（毫秒）及同步漂移趋势，区分固定错位与渐进漂移。
- [ ] A-02 采用正值表示音频超前画面，负值表示音频滞后画面；界面、接口、计算和文档保持一致，并给出公式和例子。
- [ ] A-03 明确软件播放呈现环节的音视频观测点与统一时间基准；不能仅因音视频PTS接近，就宣称内容实际同步。
- [ ] A-04 使用已知同步关系的画面与声音验证，支持复现固定偏差与漂移；对于素材本身已有错位且缺乏内容参考的外部流，明确能力限制。

### 6.3 丢帧、归因与冻结

- [ ] D-01 输出视频丢帧数量、占比，明确预期帧数、实际帧数和分母口径。
- [ ] D-02 至少区分传输环节丢失与呈现环节丢弃；可独立记录解码失败、源端主动跳帧、不可判定等情况，避免同一帧重复计入互斥原因。
- [ ] D-03 RTSP／RTMP、推／拉方向分别说明可观测证据和差异，不机械使用一套口径。
- [ ] D-04 RTP丢包不直接等于视频丢帧；须考虑帧组装、乱序、迟到、重复等。RTMP等可靠传输上的网络重传与应用层视频帧缺失不能混为一谈。
- [ ] D-05 输出单次最大连续丢帧数：同时记录当前统计窗口最大值、当前连接会话最大值；重连新建会话，历史数据保留。
- [ ] D-06 输出冻结事件与持续时间。基础冻结定义为播放中预期有新帧呈现但长时间没有新帧呈现；正常静止画面只要新帧持续呈现就不按此定义判冻结。
- [ ] D-07 不额外强制实现内容不变检测；源端重复内容与真正无新帧呈现的差异须说明。
- [ ] D-08 主动暂停、停止、启动等待、断连等状态应与运行期异常区分，不误报为正常播放中的冻结；具体事件边界写入设计。

## 7. 默认指标、告警策略与参考依据

以下是用户已接受的可配置初值，不构成已验证的性能结论。不存在统一行业门槛的数值必须标为项目策略，不得冒称标准强制要求。

| 项目 | 默认策略 | 依据性质 |
|---|---|---|
| 音画偏差 | 音频超前>45ms或滞后>125ms告警；超前>90ms或滞后>185ms严重告警 | ITU-R BT.1359-1平均可察觉／可接受边界参考 |
| 端到端延迟 | 低延迟演示档：>400ms预警、>1000ms严重告警 | 参考G.114交互业务指导制定的项目策略，不是RTSP／RTMP通用强制标准 |
| 丢帧率 | 10秒窗口，>1%预警、>5%严重告警 | 项目初始策略，须实测调整 |
| 同步漂移 | 60秒窗口拟合趋势，绝对斜率>1ms/s且持续30秒预警 | 项目初始策略；需在设计中明确预热与有效样本要求 |
| 冻结事件 | 相邻呈现帧间隔≥max(3×最近30帧平均间隔，最近30帧平均间隔+150ms) | 借鉴W3C WebRTC统计定义，由本项目自行计算，跨协议应用需说明 |
| 冻结严重告警 | 持续1秒 | 项目分级策略；稳定30fps时上述冻结判据约183ms |
| 刷新 | 指标每秒刷新 | 项目初值；单帧观测与事件检测不能只依赖1秒采样 |
| 告警防抖 | 普通越界持续3秒触发、恢复持续3秒解除 | 项目策略；漂移、冻结按各自专门条件处理 |

- [ ] E-01 异常检测结果实时输出并保存，防抖仅控制告警通知，不能抹去短时异常或原始检测证据。
- [ ] E-02 提供可配置HTTP Webhook，通知发生、升级与恢复，包含流标识、指标值、阈值、时间和归因，支持有限重试。
- [ ] E-03 用本地接收端演示Webhook，不依赖邮件、微信或云通知；看板实时更新不能单独替代对外通知。
- [ ] E-04 无效、缺失、不适用、不可测数据须与正常值区分；阈值调整、恢复滞回及多级告警状态规则写入设计。

## 8. 预览、Web看板、配置与存储

- [ ] W-01 浏览器访问看板，打开即用，不要求复杂部署；Chrome作为主要演示浏览器，Edge做兼容验证。
- [ ] W-02 任意一路实时播放预览，显示分辨率、帧率、码率、协议等基本信息；可关闭并切换其他流。
- [ ] W-03 总览页每路一卡，实时显示延迟、音画偏差、丢帧率，红黄绿标识质量状态，并区分离线和不可测状态。
- [ ] W-04 单路详情有延迟、音画偏差、丢帧率三张趋势图，支持近5分钟实时刷新；显示必要归因、冻结、漂移和事件信息以定位问题。
- [ ] W-05 历史查询支持近1／6／24小时固定范围，并支持自定义起止时间，能查询历史曲线和异常事件。
- [ ] W-06 指标与异常事件持久化，重启后仍可查询；默认指标、事件、日志保留7天，策略可配置。
- [ ] W-07 配置文件与网页常用设置并存。阈值和告警持续时间等即时生效；改变地址、协议等连接参数时重启对应任务并展示状态。
- [ ] W-08 数据保留设置可以修改，由周期清理任务执行；媒体录像采用独立容量上限或循环保留策略，不无限增长。具体上限在可行性与设计阶段确定。
- [ ] W-09 保留可追溯运行日志，详细程度可配置，记录连接、重连、指标异常、告警与必要错误信息。
- [ ] W-10 数据表达清楚、可定位问题优先于界面装饰；实现适度整洁、易于现场讲解的界面。

## 9. 非功能与验证要求

- [ ] N-01 基础并发组合连续运行1小时，无崩溃、无内存泄漏，指标在稳定输入下不发生由实现导致的明显漂移。
- [ ] N-02 用运行记录、资源采样及适当诊断支持稳定性结论，不能将“未观察到明显增长”等同于完全证明无泄漏。
- [ ] N-03 流源、阈值、告警持续时间、数据保留和日志级别均可配置，不写死在程序中。
- [ ] N-04 核心逻辑有单元测试；测量真值、计算与归因结果能核对。
- [ ] N-05 构造真实经过检测路径的高延迟、音画不同步、丢帧场景，复现检测与告警；不能只修改前端显示值或数据库数据。
- [ ] N-06 检查推拉混合并发、两种RTSP传输、异常隔离与重连、持久化、历史查询、配置生效、Webhook及一键离线启动。
- [ ] N-07 加分功能单独标记已实现、已验证、未完成或受限，交付说明与实测一致。

## 10. 加分项目标

以下均争取完成，但不能牺牲基础准确性和交付时限。顺序可以根据可行性验证调整。

| 编号 | 加分项 | 完成标准及约束 | 初始安排 |
|---|---|---|---|
| B-01 | HTTP-FLV拉流 | 支持接入，并纳入三类指标；遵守可测性与归因限制 | 较早争取 |
| B-02 | WebRTC拉流 | 支持接入，并纳入三类指标；不能只复用成品质量统计替代核心逻辑 | 高复杂度，后置评估 |
| B-03 | 推流侧质量观测 | 输出实际可观测的三类质量信息，明确本地／远端观测边界；远端呈现需反馈或配合测量 | 后置评估 |
| B-04 | 时钟偏差分析 | RTSP链路额外输出两端时钟偏差和单向延迟估计，解释条件与不确定性；估计不可替代主实测延迟 | 后置评估 |
| B-05 | 同步偏差交叉验证 | 第二种相互独立的音画同步验证手段，与主指标交叉印证 | 优先争取 |
| B-06 | 8路并发 | 稳定支持8路1080p30并发接入与检测，记录实际配置和资源占用 | 基础稳定后验证 |
| B-07 | 离线复盘 | 保留媒体、源端参考与必要观测记录，复算可恢复的指标并查看异常片段 | 基础持久化后推进 |
| B-08 | 多画面宫格预览 | 多路同时渲染，记录额外负载，不影响核心检测 | 较早争取 |

离线复盘不能仅凭录像重建当时真实网络到达或呈现丢弃情况；相关复算必须依赖同步保存的观测记录，并说明不可恢复的部分。
