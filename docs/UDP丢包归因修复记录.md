# UDP丢包归因修复记录

日期：2026-10-29。在63d6307与文档冻结基础上，按用户最新反馈仅修复UDP丢包归因，其他加分／最终长测不自动推进。源码、核心测试、单路真实包丢失及原始事实审计构成本次闭环；用户配置和未知临时文件保持原状。

## 1. 已定位问题

用户会话chain-14-1793259942046原始事实中，已有4316条RTP边界观测，却出现737条unknown_missing；其中既有已标损伤、未进入解码的源帧，也有已成功提交但未产出的帧。150个提交及141个解码输出缺源ID。同期TCP会话的接收后丢弃可归因，证明并非必须把UDP一律留未知。

原实现存在三个缺口：

1. 解码输出只要有一个无法关联，就按发生时间影响之后大量源帧；即使另一个源帧有损伤证据，也会被统一保守归未知。
2. RTP后备匹配只允许damaged源帧，且最近完整负载哈希匹配必须在500ms内。严重丢包或组帧内容变化后，完整帧和受损帧均可能漏配，产生更多无ID输出。
3. 新RTP／PTS校验初版限制到2tick，实际观测到连接内PTS偏移小幅变化，例如42tick约0.467ms；过严拒绝会再次引入一个无ID输出及一组未知。最终使用与既有源媒体候选一致的2ms界限，即90kHz下180tick；这是关联容差，不是延迟修正或常量扣除。未独立证明该偏移的全部内部成因，不将其归为网络故障。

## 2. 当前实现与分类

中继仍在真实媒体路径观测门前、成功转发后的包数和完整旁路内容，独立匹配源端哈希。FrameRecord保留RTP时间戳、marker验证及实际包数。接收完整负载哈希匹配校准源媒体PTS及RTP到接收PTS的映射；后备匹配必须有最近15秒内的真实负载锚点、同代次、唯一源媒体候选、≤2ms媒体偏差、≤180tick的RTP交叉验证和至少一个实际转发包。完整但哈希受组帧影响的候选也可据该独立边界恢复身份，不强行要求先标损伤。

无法关联的输出保存代次、观测时间及可被RTP验证的源媒体位置，只阻止可能对应的源帧被确定归因。不同代次／已知不同位置不互相影响；位置也未知时继续保守。完整RTP边界证明该帧0包转发时，不能用别的解码输出否定它的传输缺失。

| 页面分类／内部结局 | 必需证据 | 含义与边界 |
|---|---|---|
| UDP/RTP丢包：未进入解码的帧缺失／transport_lost | 源帧与RTP旁路身份、实际转发包数少于门前包数、等待成熟后无同帧成功解码提交／呈现，且没有可能属于该帧的歧义输出 | 已在观测段发生数据报损失，压缩帧未正常进入解码；不声称该结论定位了未观测的源到服务器网络 |
| UDP包不完整：已提交解码但超时未产出／damaged_decode_no_output | 同帧实际包损伤、源收关联、同代次send_packet成功，提交后默认5秒仍无对应输出，无冲突证据 | 明确包损伤与解码阶段未产出，不用“设定丢30%”代替证据 |
| 输入缺失后解码未产出（关联证据）／decode_after_input_loss | 成功提交后超时无输出，且此前有真实缺失／受损输入ID上下文 | 本帧不一定自身少包；保留与先前输入缺失的关联，不声称解析出了确切H.264参考依赖 |
| 缺失但原因尚不能确定／unknown_missing | 身份、时间映射或呈现证据不足／冲突 | 仍保留，不为清零界面而强制归UDP |

丢包但仍解出并呈现的帧仍计presented，可另看damaged_presented_frames；解码器明确拒绝输入仍是decode_failed，不冒充“成功送入但未产出”。同一源帧只计一个结局，包率与帧率分开。极晚的可靠输出可更新超时结局。

## 4. 过程验证与保留失败

- 首次修正歧义范围与损伤候选后，10%丢包／100%阻断／恢复／30%呈现对照能分类306条传输缺失、13条损伤后解码未产出，但仍有103条未知；未作为最终关闭结果。
- 加入RTP／PTS锚点后，严格2tick版本的10%完整流程剩17条未知、1个无ID输出，真实观测揭示小幅PTS映射变化。其10%与30%完整流程的结果文件保留为中间版本证据，不能称最终180tick二进制已完成相同全部矩阵。
- 最终二进制首次短测在无故障基线出现1帧已明确归因为呈现调度丢弃，原“必须任意结局全零”判据中止并自动清理。专项基线随后改为无未知／无传输或解码损失，允许≤1%的已有明确呈现丢弃；不删除这帧或宣称绝对无抖动。最终恢复仍要求无缺失且输出正常。
- Release构建与四项CTest通过，覆盖歧义输出的媒体范围／代次、完全未转发与部分损失、未知保守、RTP回绕及容差边界。四项现有Node测试通过，中文分类显示断言同步。

## 5. 未外推范围
