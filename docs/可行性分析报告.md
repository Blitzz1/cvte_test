## 1. 结论与适用范围

建议采用 **Windows x64＋C++20＋CMake＋MSVC v143**，以 **FFmpeg** 完成媒体接入与编解码，**MediaMTX** 作为本机媒体服务，**SQLite** 保存指标与事件，**cpp-httplib** 提供HTTP接口与Webhook，轻量网页承载看板。

三类指标的计算、参考匹配、时间模型、归因、统计窗口和告警状态机由本项目自行实现。SDL3作为软件播放输出的首选候选；呈现时序能力不足时，评估Windows原生呈现与音频时钟接口。

这是明确的初版推荐，不是已验证的可交付结论。常规组件可以按此方向准备；**源端参考、软件呈现观测、分层丢帧归因是三个核心阻断风险**，必须先完成小型验证。验证失败时调整实现路径，不能以估计值、预定播放时刻或统一“不可判定”代替原始要求。

不再对已经确认的语言、平台和需求做无边界比较。验证仅围绕真正可能使方案不可行的能力开展。

## 2. 目标、验收与约束

- 基础协议为RTSP 1.0（UDP与TCP）、RTMP，均支持推拉；编码为H.264＋AAC。
- 同时运行4条完整1080p30含音频的源端→推流→本机服务器→拉流→播放呈现检测链路（RTSP 2条、RTMP 2条）。本程序管理每条链路对应推拉任务，4推＋4拉按4路计；8路加分为8条完整链路。
- 测量端到端延迟、音画偏差及漂移、丢帧及归因、连续丢帧与冻结。观测位置、窗口、单位、阈值必须清楚。
- 主验收使用普通音视频素材，源端音画同步作为输入前提，不依赖叠字、声音标记或自定义SEI；程序管理源端及接收端，允许记录全链路可取得的原始信息。独立外部源依据不足时显示不可测／不可判定并说明原因。
- 软件播放呈现是主指标终点；浏览器预览额外链路不自动纳入主延迟。各路独立运行观测，不把解码完成当成呈现。
- 统一命令启动，本地运行，不购买设备、不依赖云服务，演示依赖提前准备。
- 指标与事件持久化，固定及自定义时间查询、Webhook、网页常用配置、日志和保留策略均需实现。
- 基础场景连续运行1小时；尽可能完成8项加分目标，不牺牲基础可信度。
- 10月29日14:00前就绪为目标，最晚16:00；完整需求和阈值以需求基线为准。

## 5. 组件选择、原始数据层级与边界

### 5.1 主要组件

| 组件 | 初步职责与理由 | 原始数据／接口层级 | 不应假定的能力 |
|---|---|---|---|
| FFmpeg：libavformat | RTSP／RTMP读写、文件及封装处理；同一API体系减少重复接入 | 压缩媒体包、流信息、媒体时间戳及时间基等 | `AVPacket`不是网络RTP数据包；不能默认公开每个RTP序号、真实采集时间或实际呈现时间 |
| FFmpeg：libavcodec | H.264／AAC解码，源端编码或适配 | 编解码输入输出、解码视频图像及音频采样、相关帧属性 | 解码成功不证明网络未丢帧、内容同步或已经呈现 |
| FFmpeg：libswscale／libswresample | 像素格式与音频格式转换 | 转换前后像素／采样数据 | 转换耗时、重采样与缓存必须纳入观测，不自动提供播放时钟 |
| MediaMTX | 本机接收和转发RTSP／RTMP，提供浏览器预览候选HLS路径；独立可执行程序便于启动管理 | 媒体服务和配置层；不是本项目核心指标计算器 | 不承诺任意自定义元数据原样保留，也不假定其提供HTTP-FLV输出 |
| SDL3 | 软件视频渲染及音频输出的首选候选，减少设备与窗口基础设施代码 | 渲染调用结果、音频流队列等输出接口 | 渲染调用返回不等于像素实际发光；音频队列字节数不等于硬件已播放采样数 |
| SQLite | 嵌入式指标／事件持久化，无需额外数据库服务 | SQL记录、事务、索引与WAL | WAL并不允许任意多写者同时提交，也不替代容量和清理管理 |
| cpp-httplib | 本机HTTP API、静态资源、Webhook客户端；依赖少 | HTTP请求响应、连接与错误状态 | 阻塞I/O不能占用媒体工作线程，通知须独立队列且有超时 |
| nlohmann/json | JSON配置、API和事件序列化 | 配置与结构化业务数据 | 类型校验和业务校验仍需自行实现 |
| spdlog | 分级和轮转日志 | 程序日志记录 | 日志不能替代帧级测量记录，也不能无限增长 |
| Catch2＋CTest | C++核心单元测试与测试调度 | 测试输入输出和断言 | 单元测试不能代替真实协议、播放和长时间验证 |

FFmpeg的协议文档描述RTSP读写及UDP／TCP选项；`AVPacket`、`AVFrame`文档描述媒体数据和时间戳属性。这些为初步选型提供依据，不能证明本项目已获得包层或呈现层全部信息。[S1][S2][S3]

MediaMTX官方介绍列出了发布、读取与协议转换能力；实际H.264／AAC互通、时间戳改写和元数据保持仍以实验为准。[S4] SDL输出接口的意义需要按官方语义解释，不能由函数名推导出物理显示／发声时刻。[S5][S6]

### 5.2 网页、预览与实时数据

- 看板使用本地HTML／CSS／JavaScript，趋势图优先自行用Canvas绘制，避免额外前端构建链。
- 指标每秒刷新，初版采用HTTP轮询；4路／8路规模先验证，不为指标传输强制增加WebSocket依赖。
- 浏览器预览首选MediaMTX HLS＋本地打包的hls.js，在Chrome／Edge播放H.264／AAC；支持声音及切换。hls.js基于浏览器MSE，具体互通与延迟待实测。[S4][S8]
- HLS只是浏览器预览适配路径，不增加“必须检测HLS输入”的基础范围，也不改变RTSP／RTMP主检测链路。
- 预览时延与主检测延迟分别说明；有明显启动等待或过大延迟时，先优化分片／缓冲，再评估fMP4／MSE直接适配。不能以截图轮询替代含音频实时播放。
- WebRTC预览可能涉及音频兼容／转码，不能因服务器支持WebRTC就认定AAC可直接播放；其作为后续加分接入方案单独验证。

## 6. 自行实现与第三方职责的界线

**自行实现**：源端实时参考记录与帧关联、统一时间模型、延迟计算、音画偏差及漂移、分层丢帧与去重、分母与窗口、连续丢帧／冻结、指标有效性、告警状态机、异常注入控制、观测记录与验收核对逻辑。

原始计数可以作为证据输入，但不能直接照搬播放器／服务器／浏览器成品QoS统计作为三类主指标。若需要低层适配或补丁，应限定在导出原始观测，检测计算仍放在项目模块中。

## 7. 关键测量路径的初步方案

### 7.1 源端参考与延迟

源端按实时节奏处理普通文件，实际进入链路时旁路记录`会话ID、流ID、内部帧ID、源媒体时间、源端参考时间`及必要发送观测。内部帧ID用于记录系统，不插入媒体内容。同机优先使用可比较的高分辨率单调时钟，并明确单位及进程间可比条件；UTC用于查询和显示，不用受墙钟校时影响的差值作为核心耗时。文件PTS或推流启动时间均不能替代逐帧实际送入链路的参考时间。

正式方案不采用画面水印、声画插入标记或自定义SEI。优先调查源端与接收端已有PTS／DTS、时间基、协议时间及媒体单元关系，结合可取得的服务器接收／转发观测建立映射。每个映射必须处理时间戳改写、帧重排、重复时间戳、循环与重连，不能用接收序号直接对应源端序号，因为丢帧会使该关系失效。

必要时评估不改变原内容的压缩媒体载荷比对或解码内容特征匹配，用于辅助验证关联；容器变化、NAL表示变化、转码和重复静止帧可能破坏唯一性，不能预先保证字节哈希或相似度即可解决全部匹配。无法唯一关联的样本明确标无效，主验收仍必须验证普通素材上存在可靠的测量路径。

“全链路已知”解释为两端及本机服务器可管理、允许采集必要原始信息，不是未经验证地认为所有底层事件已经暴露。每个组件提供的实际字段、缺失观测及补充适配都须在V-01／V-03中记录。

主延迟为已匹配源端帧到**已定义的软件呈现观测事件**的差值；预定调度时间、解码完成时间单独保存用于解释，不替代主指标。

### 7.2 音画偏差与漂移

用户已明确：源端普通素材是音画同步的，检测目标是链路是否使拉流播放失去这种同步关系，不承担任意素材口型识别或源素材内容对齐修复。

主路径保留源端音视频原有时间对应关系，将其映射到统一源媒体时间轴；接收端观测已呈现视频的源媒体位置，以及音频实际播放进度对应的源媒体位置。在同一可比较观测时刻分析两者是否偏离源端同步关系，正值表示声音超前、负值表示滞后。不能分别将音视频首帧都归零而抹去原有偏移，也不能只比较接收队列中最近的两个PTS。

音频已提交字节数不等于已播放样本数，视频提交不必然等于呈现完成。需验证音频消费时钟、输出缓存与视频观测的时刻对应，记录帧／采样量化误差与设备边界。压缩帧重排、AAC编码延迟、重采样与缓存必须纳入时间模型，不能任意减去常量让结果接近零。漂移由足够有效样本拟合，预热期不输出虚假稳定结论。

验收使用普通同步素材经过实际固定或渐进延后，比较独立观测结果与实验真值。专用闪光／声音参考素材可作为额外校准测试，但不预处理正式素材，也不作为主算法运行前提。第二种独立同步交叉验证仍作为加分项评估，不再默认通过在正式媒体中插入标记完成；只把相同计算换一种展示不算独立验证。

### 7.3 丢帧与归因

初步记录链路：`源端生成 → 编码／发送 → 传输接收 → 解封装／解码 → 播放队列 → 软件呈现`。以帧ID和会话关联各阶段，使用互斥归因，证据不足单列。

- RTSP UDP：需要包层序号、RTP时间和帧组装证据；不能只看`av_read_frame`输出。优先评估可控链路中的自研接收边界观测／故障注入适配；如公开接口不足，再比较最小FFmpeg观测补丁与受控代理方案，不能假定已有透明抓包能力。
- RTSP TCP：需要区分RTP交织媒体记录、队头阻塞和应用丢弃；TCP重传不是最终视频帧丢失。包层观察方式独立验证。
- RTMP：依据已实际发送的媒体帧、接收帧、解码和呈现记录定位；网络重传不能直接算丢帧。若要证明中间服务或接收阶段丢弃，需建立明确受控边界，单凭源收帧号缺口不能确定具体网络原因。
- 主动源端跳帧、解码失败、呈现丢弃与未知原因分别记录；按实际可辨识层级给结论，不把所有源收差异统一归为传输丢失。
- 演示注入必须真实发生在标明的位置：发送前跳帧、UDP包丢失、接收后呈现丢弃是不同实验，不能互相替代。

### 7.4 本机服务器与独立故障注入

采用Windows版MediaMTX接收和转发本程序推送的媒体，随后由对应拉流任务取回。服务器运行在本机不等于省略传输：127.0.0.1仍经过套接字和系统协议栈，没有外部物理网络；基线环境可能损伤很少，资源或队列问题仍可造成异常。本机结果不代表公网性能。[S4]

故障注入模块按链路启停，支持固定随机种子、随机比例与连续丢弃，实际记录受影响的包／帧及发生位置。初步实验矩阵如下：

| 实际注入位置／动作 | 核对目标 |
|---|---|
| RTSP UDP传输边界丢RTP包 | 自研包层观测及实际受损／缺失帧归因；包数与帧数分别核对 |
| 明确媒体转发边界丢完整视频帧 | 对应阶段帧丢失；与源端主动跳帧区分 |
| 已解码帧在播放前丢弃 | 呈现丢弃、连续丢帧及可能冻结 |
| 实际增加链路或播放等待 | 端到端延迟的实测变化与告警 |
| 实际延后某一音视频分支，逐渐改变等待 | 固定音画偏差、漂移、告警与恢复 |

RTMP／RTSP TCP的重传与阻塞实验不能由任意删除字节替代；完整媒体帧丢弃必须选择协议有效的边界。具体适配方式仍受V-03验证，不提前声称现成组件已支持全部注入能力。

注入决策与检测逻辑分离；检测模块只消费正常测量所需参考与实际观测，测试工具事后读取注入真值核对结果。不能直接用“设定丢5%”生成“检测到5%”。固定随机种子便于复现决策，但线程与网络调度造成的后果仍需记录。

现场验收先展示4条正常链路，再单独损伤1条，观察指标、归因、告警、恢复、历史和其他3条的隔离表现。

## 9. 资源、存储与部署的初步估算

- 一帧1080p YUV420约3.1MB，4路原始30fps数据流量约373MB/s，8路约746MB/s；这是像素体积推算，不是CPU／GPU性能测试。减少重复拷贝，帧队列必须有界。
- 不默认每路同时实时重编码多个版本；先验证必要源端编码及接收解码，能合法复用的压缩媒体可复用，但不同检测流仍独立管理。
- 上述原始像素流量仅为单阶段体积估算；完整4／8条链路另有源端编码、服务器转发、拉流解码、软件呈现、故障注入与浏览器开销，不是全系统吞吐或内存带宽预算。
- 每路每秒1条聚合样本，4路7天约241.9万条，8路约483.8万条；具体SQLite空间取决于字段、索引和事件密度，须实测。建议单写入队列、批事务、WAL及按流时间索引。[S7]
- 若每路录像码率4Mbps，4路约7.2GB／小时，8路约14.4GB／小时，不含容器等开销；4Mbps仅为容量示例，不是已确认编码参数。
- 媒体保留建议初值为全项目总量10GiB上限或最近30分钟先到者清理，可配置；该数值是本报告提出的实现初值，未改变已确认的指标／事件／日志7天保留。正式采用前核对可用磁盘与有效复盘时长。
- 首次依赖准备允许联网，演示启动不联网；开发SDK不必随运行包全部携带，实际运行DLL、服务器、前端资源、配置及许可证需完整归档。
