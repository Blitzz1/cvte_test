# AVQualityMonitor 可行性分析报告

> v1.0，2026-10-29按已落地实现修订。初版及实施前候选在Git历史保留；本文不再把候选库、待做原型与当前实现混写。程序基线63d6307，当前暂停功能改动。

## 1. 结论与条件

Windows x64、C++20、MSVC14.44、CMake／Ninja、FFmpeg、MediaMTX、WIC／WASAPI、SQLite和本地静态网页组成的方案已落地。普通未标记文件能够完成本机源端推流→服务器→接收解码与软件输出，并提供三类指标的可追溯分项证据。

可行性是有边界的：文件实时释放为源端参考；素材自身同步；软件像素／设备消费为终点；有歧义时保留无效或未知。四路旧版一小时达到报告中的运行／资源门槛，但最新版本一小时及原生浏览器／离线最终验收未完成，不能据此承诺全场景精度、无泄漏或稳定8路。

## 2. 已采用选型及原始数据层级

| 组件 | 选择理由及提供的数据 | 自研边界与限制 |
|---|---|---|
| C++20／MSVC14.44／CMake | 直接调用C接口媒体库及Windows API，RAII／线程管理；已构建运行 | 不要求用户安装另一运行平台；使用已验证工具集而非预览版 |
| FFmpeg libavformat | 文件读写、RTSP／RTMP接入、封装／解封装、压缩包及PTS／DTS／time_base | AVPacket不是网络数据报，不自动提供源拍摄时刻或物理呈现 |
| libavcodec | H.264／AAC解码、输入返回状态、视频图像与PCM | 解出不等于已呈现；不以现成QoS模块代算指标 |
| libswscale／libswresample | 像素及PCM格式转换 | 转换与队列时间由本程序观测，非播放时钟 |
| MediaMTX1.21.3 | Windows独立进程，本机发布／读取RTSP、RTMP，按需HLS对照 | 不提供本项目逐帧质量结论；本机回环仍经过socket和协议栈 |
| Direct2D／WIC | 真实绘制完成并锁定可读像素，系统SDK可用 | 不代表物理屏幕扫描／发光；镜像JPEG另有网页展示延迟 |
| WASAPI | 每路实际音频消费位置、频率及PCM边界映射 | 只用同代次、新鲜且有效样本；不声称声学到达 |
| SQLite3.50.4 | 嵌入式指标／事件，WAL、索引及范围查询，无数据库服务部署 | 持久化与清理自研；不等于保留完整接收录像 |
| cpp-httplib0.28.0／json3.12.0 | 本机HTTP、Webhook、JSON配置及事件 | 异步控制／通知、校验与有限队列由本程序实现 |
| HTML／CSS／JS／本地hls.js1.6.13 | 看板无需前端构建或运行时CDN | 检测预览复用WIC；HLS仅原流对照，不能替代检测输出 |
| 项目日志与CTest断言目标 | 减少运行依赖；异步轮转日志、核心测试已实现 | 未采用spdlog、Catch2；单元不能代替实流或长测 |

SDL3曾是候选，最终未采用；Qt、GStreamer、Docker／WSL及独立数据库不是本项目运行前提。精确依赖版本、哈希、构建和许可见[依赖环境](./依赖与运行环境.md)与[第三方说明](./第三方组件与素材.md)，不为文档整理重新下载或升级。

## 3. 三类测量如何成立

源端按DTS实时释放文件压缩单元，旁路保存内部ID、源媒体时间、单调释放时刻和规范化签名。接收压缩内容匹配源端，H.264忽略封装表示差异、仅取VCL负载；AAC使用原始负载。多候选用已验证时间偏移辅助消歧，仍不唯一不硬配，不给媒体插入标记。

接收接口返回后立即打点，再哈希／锁／查找；同帧到WIC完成得到完整端到端，卡片单列释放至完整压缩帧返回的传输段，所有分段真实打点。当前RTSP约一帧额外等待已有UDP帧末事实与FFmpeg源码支持，是当前解析路径现象，不是协议固定规定或纯网络时间。

音画同步在视频完成时比较统一源媒体轴上的音频消费进度和视频进度，不分别将音视频首帧归零；普通同步素材的固定延后和渐变实验已验证符号与相对变化。它不分析任意素材口型，也没有独立物理校准。

丢帧用源视频记录追踪接收／提交／解出／呈现互斥结局。UDP中继提供序号和帧损伤事实；TCP底层丢包／重传未统计。默认成熟等待及未知上下界防止把在途或歧义强判丢失。注入实际作用于数据报、完整压缩单元或呈现队列，真值另存，仅事后核对。

## 5. 本机部署与资源可行性

本机i9-12900H、约32GB内存、Iris Xe和SSD为已用环境，但用户办公本散热弱，不依硬件名称承诺持续负载。文件源当前重封装推送，未为每路重新编码视频；各路完整解码1080p，软件输出缓存默认320×180，每路96帧／20MiB、共享像素64MiB、解码1线程。这是资源边界，不是降低输入负载或证明进程内存上限。

程序、MediaMTX与浏览器本机运行，不买设备、不用云。启动前缓存依赖和素材；脚本用时限、PID／路径／创建时间保护收尾。数据库和分段日志有保留策略，默认不保存完整接收媒体，完整离线复盘仍未完成。

## 6. 开发与文档安排

原四天计划遵循：需求与初版可行性→关键能力验证→核心设计／测试计划→最小测量闭环→4路、存储告警与界面→分层回归→冻结版本后长测、离线与演示。可行性在启动后2天内提交、设计3天内初版，后续随实现修订；实际提交时间由Git记录，不倒写。

当前实现与专题验证已完成至分项回归阶段，用户暂不继续改动程序。后续若恢复，先处理[剩余验收](./需求追踪与验收状态.md)，每次改动先写受影响设计和测试判据，再代码、验证、文档同步和简短Git提交；不把早期计划重复当作尚未实现任务。
