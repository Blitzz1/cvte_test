## 1. 已落地结构与依赖

CMake + Ninja + MSVC 14.44，C++20。FFmpeg 负责协议、封装、解码和格式转换；自研源收关联、时钟映射、延迟与同步计算、丢帧归因、RTP 序号状态和告警。SQLite WAL 存储；cpp-httplib 提供 API；本地 hls.js 供浏览器额外预览。没有采用成品 QoS/QoE 检测模块。

软件视频后端已选定 Direct2D WIC 软件表面，不使用规划中的 SDL。四／八路图像按格绘制到真实的 1000×600 输出表面，原始输入／解码仍为 1080p。`EndDraw` 后成功锁定实际像素才产生 `software_present` 事实。可选 `show_monitor:true` 将该像素表面拷贝到原生窗口；窗口缩小或隐藏不停止软件表面输出。主指标不声称已经显示器扫描／发光，原生窗口二次拷贝和浏览器 HLS 不计入主终点。

WASAPI 每路独立音频会话，设备消费位置除以报告频率得到流时间，再通过实际提交的 PCM 段映射回源媒体时间。设备读数与 QPC 相关联后，在视频输出时采样同步偏差。失效／过旧读数返回空值。监听按钮只改变音量，所有路仍有音频消费观测。[设备位置语义](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)

## 2. 当前指标口径

| 指标 | 实施窗口／单位 | 有效性与限制 |
|---|---|---|
| 端到端延迟 | 每匹配视频帧实际输出减源端释放；近1秒均值、最大值，ms | 输出过旧或没有源端匹配则空；文件释放不包含原文件采集编码 |
| 音画偏差 | 视频输出时，对齐新鲜设备消费位置；近1秒中位数，ms | 正值音频超前；依赖源端媒体时间共同基准和源素材同步 |
| 同步漂移 | 最近60秒有效同步样本线性拟合，ms/s | 连续跨度大于48秒、样本多于40个；突变／缺口切段，残差大于15ms不发布斜率 |
| 视频丢帧 | 默认源帧年龄5～15秒的10秒成熟窗口，%／帧数 | `resolution_timeout_ms` 控制成熟等待；启动首次有效输出前的源帧排除，避免把未订阅帧算网络丢失 |
| 连续丢帧 | 按源媒体顺序，成熟窗口连续最大值并保留本会话最大值 | 分母为确定结局；未知缺失单列，不强行归因 |
| 冻结 | 新输出间隔，阈值 max(3×近期平均间隔，平均间隔+150ms) | 没有新图像提交才冻结；不把素材静态画面直接判冻结 |
| RTP 包丢失 | UDP 视频 RTP 序号，允许64包重排后确认缺口，会话累计% | 与视频丢帧独立；仅支持经过本项目8555中继的UDP路径，TCP／RTMP不伪造包级结果 |

默认阈值：延迟400／1000ms、丢帧1／5%、音频超前45／90ms、滞后125／185ms、漂移1ms/s持续30秒、冻结严重1000ms；一般告警持续及恢复各3秒。音画阈值基于需求文档 BT.1359 基线；其他项目策略及参考依据见需求基线，不声明这些数字均为行业强制标准。

## 3. 普通素材关联与分层归因

H.264 VCL NAL 规范化后 SHA-256 关联，忽略 Annex-B／AVCC 分隔方式及非画面配置单元；AAC 使用原始负载。哈希只在旁路记录中使用，不修改发送素材。多个候选需时间戳偏移辅助消歧，仍不唯一则未知。FFmpeg `AVPacket.opaque_ref` 仅在本地将已关联身份传递给解码结果，不穿越网络。

UDP 中继在媒体路径真实接收／转发 RTP，独立记录帧边界和门前门后包数；注入器真实阻断选中的数据报。检测使用实际转发观测，不读注入随机决定。无法从当前观测断定具体原因的缺失进入 `unknown_missing`。RTSP TCP／RTMP 的可靠传输不报告 UDP 意义的包丢失；完整访问单元在接收后丢弃归为 `receiver_discarded`，解码后丢弃归为 `presentation_dropped`。

原生窗口或浏览器显示更慢不改变已完成的软件表面测量；现场讲解必须说明软件终点，不能称物理玻璃到玻璃延迟。单独外部拉流没有源端旁路参考时，绝对端到端延迟和精确源帧丢失不可判定，不能用接收 PTS 差代替。

## 4. API 与配置

实际 API 前缀 `/api/v1`；JSON 直接返回对象／数组，尚未采用设计初版拟定的统一 data 包装。

| 路由 | 方法 | 行为 |
|---|---|---|
| `/health` | GET | 健康、时间与本机写操作令牌 |
| `/chains` | GET | 各路状态、实时指标与有效性 |
| `/config` | GET / PATCH | 获取／校验／原子持久化配置；revision 不符返回409 |
| `/chains/{id}/start`、`stop`、`restart` | POST | 返回202与command_id，控制线程执行 |
| `/commands/{id}` | GET | queued／running／completed／failed |
| `/chains/{id}/metrics?from=…&to=…` | GET | UTC毫秒范围历史（最多8天查询跨度） |
| `/events?chain=…&from=…&to=…` | GET | 历史事件，默认最近24小时 |
| `/chains/{id}/fault-injection` | POST | 实际故障配置；空对象恢复默认 |
| `/audio` | POST | index 指定监听路；-1静音 |
| `/shutdown` | POST | 有序退出 |

POST／PATCH 带 `X-AVQM-Token`，服务绑定127.0.0.1，无公网部署授权。通知为独立 HTTP Webhook 队列，三次有限重试和结果事件；`/webhook-demo` 是本机示范接收器。通知队列目前在内存中，进程退出丢失未发送任务，事件本身已持久化；HTTPS及持久出站队列尚未实现。

日志级别可配置，队列有上限；按10MiB或跨日轮转，历史分段按保留天数清理。指标、事件及历史日志默认保留7天，周期清理；观测文件100MiB分段、过期分段同样清理，当前活动文件需持续分段后才能到期。注入真值保留本机文件；这些文件不等于已完成“离线媒体复算”加分项。

## 6. 第二轮实施补充

- 文件循环保持同一推流连接，通过连续封装时间戳推进，编码内容不变；不再每次播完重连。真正发送失败时清理关联和播放纪元再重建。
- 对未唯一关联但可能已经输出的源帧，不把“未关联”直接认定为已证实丢失：`loss_pct`为可能损失上界，`loss_confirmed_pct`为已证实下界，`loss_unknown`和`loss_validity`说明限制。看板有未知时以“≤”标记；原始事实仍保留。全部成熟帧可确定时上下界一致。
- 新增 `src/http/flv`：从既有发布流提取原始压缩数据，重封装为HTTP-FLV，`/flv/{chain_id}.flv`供直播拉取；不支持文件字节范围跳转。配置例见 `config/http-flv.json`，设protocol为httpflv、publish_url为RTMP、pull_url为本机FLV接口。自研检测沿用源端旁路关联，不依赖转封装库的成品质检结果。
- HTTP-FLV初版为确认流参数设置较长探测，会增加约0.9秒启动／播放延迟；指标如实包含此段，可能触发默认延迟严重告警。尚未进行低延迟优化或完整故障矩阵回归。
- 网页新增额外HLS宫格，四路及八路已实测同时播放1080p画面；八路主链路短测已通过，完整浏览器兼容性仍需演练。
- 历史降采样按时间桶保留延迟峰值、同步正负极值和丢帧峰值对应的真实样本，不生成不存在的合成点。长查询最多5000点。
- 告警载荷附带阈值、指标快照、时间和归因；通知失败三次尝试后记录失败。运行日志、逐帧事实和通知结果仍分别保留。

当前补充：码率按近1秒压缩负载计算；接收重连记录独立receiver_connection并重置连接统计与播放纪元。冻结恢复时将完整间隔、阈值及超阈值持续时间写入freeze事件，短于严重告警门槛的冻结也保留。网页事件支持固定范围与自定义起止，观测缺失不会显示正常绿色。

## 7. 基础性能与测量修正（2026-10-27）

视频CPU像素缓存默认320×180，保留完整1080p解码；默认每路队列20MiB／96帧，共享像素64MiB。源ID索引、增量格子绘制、有界异步证据写入及单线程解码降低积压风险；这些限制不等于整个进程内存上限。

图像、音频段和音频设备采样均携带playback_generation；重连清空旧代次窗口及校准。同步仅在15ms新鲜度与有效PCM段内使用设备读数，缺口和偏差突变切分漂移段。新增connection_state、output_health、latency_validity、sync_validity、drift_validity、evidence_validity及队列／预算／丢弃计数，网页诊断区显示其状态。

资源字段可在settings配置：output_width／output_height、video_queue_frames、video_queue_mib、video_total_mib、decoder_threads。输出尺寸、解码线程和每路队列限制在下次连接建立时加载；修改后重启对应链路。共享像素总限额立即约束新分配，降低限额不会强行释放正在使用的图像，需等待存量释放。阈值仍即时生效。API中的output_width／output_height表示配置的尺寸包围盒，实际等比例图像可能更小。

四路限时故障回归的应用私有内存峰值约127.74MiB、恢复输出约30fps；延迟和音画偏差的原始复算通过。本轮没有进行一小时稳定性验收，八路长测历史失败结论仍有效。完整方法、失败修复、数值和证据见[性能与测量修正验证记录](./性能与测量修正验证记录.md)。
## 8. 基础缺陷闭环（2026-10-28）

漂移突变分段现在要求相对基线超过50ms、同方向至少3个有效样本且持续至少100ms，候选期drift_validity为step_confirmation_pending；单帧真实迟到保留原始值，不立即清空连续趋势。缺口大于0.5秒、时间倒退或代次变化仍立即切段。普通B帧素材注入5ms/s时，实测约−4.96347ms/s，原始事实拟合复算一致。

前端服务断开时清空实时卡片指标并标记服务未连接，不保留绿色正常假象；后台恢复后重连。新增存储重启／保留期隔离测试，CTest现有三个目标通过。完整功能、差分误差和页面验收见[基础功能闭环验收记录](./基础功能闭环验收记录.md)。本轮内置浏览器通过不代替原生Edge／Chrome现场兼容性，仍未通过四路一小时验收。

## 10. 默认素材切换历史与后续修复

此前app.json revision 4及普通素材显式配置使用Sintel 1080p24／AAC；缓存预算、解码线程与阈值保持原设置。八路、HTTP-FLV及外部拉流示例source字段也同步为普通文件。1080p30合成配置保留为stability-four.json，run-stability明确使用它，避免24fps输入被28fps规则误判。

本次四路普通素材限时检查输出约24fps并正常清理；UDP成熟窗口111／240帧未知、2呈现丢弃，上界47.083%而中继RTP缺口为0。该次仅凭后半段观测尚未定位原因；后续解码记录及MediaMTX日志确认上游大帧UDP接收突发损失，4MiB服务器缓冲修正后原素材跨循环复验完成。默认revision 5恢复30fps；manual-start／no-audio配置与解码原始事件见UDP修复记录和素材操作指南。旧快照与新证据分开保留，新版本一小时未重跑。
