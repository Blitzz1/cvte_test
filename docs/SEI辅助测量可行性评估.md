# SEI辅助测量可行性评估

> 2026-10-29状态确认：仅保留方案评估，未实现、未纳入主测量，当前不继续开发。历史建议不构成自动推进任务。

> 2026-10-27，应用户提出的新思路评估。结论：适合在可控源上作为可选帧身份及源端时间核对路径；当前不替换普通未标记素材主方案，不把方案评估当作已实现或已验证。

## 1. 不重新编码与不改码流是两件事

H.264的SEI是补充增强信息，可以在编码完成后增加user_data_unregistered消息；无需重新压缩画面，也可以保持原有VCL画面NAL逐字节不变。但完整码流增加了NAL／数据，包大小、分包和丢失特性可能改变，不能仍描述为“完全没有修改编码后的媒体”。这并不等同于画面加水印或损失画质。

FFmpeg提供h264_metadata的sei_user_data选项，说明编码后插入有现成承载能力；该选项的固定字符串示例不等于逐帧真实采集时间生成器。动态时间、帧身份、接收解析及检测公式仍需项目实现。[FFmpeg位流过滤器文档](https://ffmpeg.org/ffmpeg-bitstream-filters.html)

## 2. 当前协议与实现的适配

| 路径 | 判断 | 必须验证的条件 |
|---|---|---|
| RTSP／RTP／UDP | 协议可承载H.264 SEI | NAL边界、聚合／分片重组、丢SEI不等于丢画面，服务器与8555中继保留情况 |
| RTSP／RTP／TCP | 同样可承载 | TCP交织不会自动保证应用不删除SEI；验证完整接收及帧关联 |
| RTMP／FLV／H.264 | AVC NALU负载有承载路径 | AVCC长度字段、DTS／CTS、服务器重封装保留及解码器输出关联；不要把NAL内SEI误当成AMF onMetaData |
| HTTP-FLV扩展 | 与AVC NALU承载相容 | 本项目重封装输出是否保留；属于加分范围，后置验证 |
| 浏览器额外HLS预览 | 可能继续承载，但不作为本方案读取端 | HTML视频播放不能直接充当项目自定义SEI读取接口；由C++接收／解码端取值 |

RFC6184明确SEI等无独立时序NAL使用所属访问单元主画面的RTP时间戳；它支持传输，但不赋予自定义时间戳绝对准确性。[RFC6184，5.1等节](https://www.rfc-editor.org/rfc/rfc6184.html)

FLV的AVCPacketType=1承载AVC NALU，与CompositionTime字段共同承载视频。MediaMTX官方列出RTSP及RTMP的H.264支持；这不足以证明本机1.21.3版经过各路径后保留每一条自定义SEI。因此当前结论是标准上可行，本机透传矩阵尚待实测。[VSO文档的旧版FLV头定义](https://github.com/veovera/enhanced-rtmp/blob/main/docs/enhanced/enhanced-rtmp-v2.md#pre-2023-videotagheader-format)、[MediaMTX RTSP](https://mediamtx.org/docs/read/rtsp)、[MediaMTX RTMP](https://mediamtx.org/docs/read/rtmp)

FFmpeg AVFrame支持AV_FRAME_DATA_SEI_UNREGISTERED，格式为16字节UUID加自定义负载；可以尝试在软件H.264解码后直接获得关联到该画面的SEI。仍需验证B帧重排序、丢失、重复、循环与重连；不能按接收包序号硬配输出帧。[FFmpeg AVFrame文档](https://ffmpeg.org/doxygen/8.0/group__lavu__frame.html)

本项目现有signature只对H.264类型1～5的VCL内容计算规范化哈希，忽略SEI。因此可以同时获得“原始VCL指纹关联”和“SEI身份关联”两个结果，无需为了实验重写主算法。该代码事实不证明任何服务器已经透传SEI。

## 3. 能验证什么，不能验证什么

| 指标 | SEI的价值 | 保留的限制 |
|---|---|---|
| 帧身份与源收关联 | 显式stream／epoch／frame_id，减少重复画面及时间戳歧义，能与VCL哈希逐帧核对 | 仅对源端可插入标记的流适用；SEI损坏或剥离必须降级，不把标记缺失当作视频必然丢失 |
| 端到端视频延迟 | 携带真实source_release时间，在实际软件呈现完成时相减，核对主方案的源帧／时间选择 | 接收时解析只得到源到接收延迟；终点仍必须等实际呈现。同机共享时钟可比较，跨机要时钟同步／映射与误差预算 |
| 丢帧与归因 | 用已知源端帧集合和SEI输出记录补充帧身份，帮助找出缺失范围 | 跳号不能单独区分传输、解码、呈现；仍需各边界观测。SEI与画面可能分包分别丢失 |
| 音画同步 | 核对视频源媒体时间和视频身份，间接检查同步计算的视频侧 | 视频SEI不说明音频在扬声器／WASAPI消费到了哪里，也不证明源素材内容同步。实际音频观测和源音视频对应关系仍需保留 |
| 独立交叉验证 | 对身份和源端时间形成另一条关联路径，能检测哈希错配等问题 | 两路径共用源时钟、WIC终点、音频设备时钟，无法发现这些共享观测的所有错误；仅增加SEI不能宣称已完成独立音画同步验证加分项 |

若是在实时采集后才于编码出口打“当前时间”，测量起点就变成编码出口；无法凭此恢复采集或编码耗时。本项目文件源应继续使用实际实时释放的source_release时刻，不把原文件PTS或离线插入时刻当真实推流时刻。

## 4. 建议的可选设计

保持普通素材主验收默认关闭SEI；明确独立实验开关，不在未知情况下修改用户原文件。仅对本程序控制的发送流临时插入，不覆盖现有UUID的其他SEI，不删除画面原有HDR／字幕等信息。

消息至少含项目UUID、schema版本、流与源端代次、帧身份、时钟域标识、源端释放时间、原始源媒体时间，以及长度／校验。校验防误解析，不等于认证。插入到与画面同一访问单元的正确位置，处理RBSP转义和AVCC／Annex-B边界；遇到B帧必须以画面身份和PTS语义关联，而不是按发送／到达顺序。

以约80字节元数据／帧粗算，30fps约2.4KB/s，即19.2kbps／路；八路约153.6kbps，尚未计NAL转义、封装与额外网络头。这只是容量估计，实际开销应测量，不能据此保证零性能影响。相较重新编码，元数据写入预期较轻，但需要新增解析、异常路径与测试。

主结果与SEI辅助结果分列，报告一致／不一致／SEI缺失／源参考缺失等状态。两条路径应独立解析身份后再比较，不能拿主方案匹配出的ID填充SEI结果；故障注入真值也不能作为检测结果输入。

## 5. 实验及采用条件

1. 离线小样本先证明：加入UUID消息后VCL字节及解码画面不变，既有SEI保留；动态逐帧身份正确。
2. 单路限时验证RTSP UDP、RTSP TCP、RTMP的无损透传、B帧关联、循环和重连代次；记录完整数目、缺失率、错误率、CPU及字节开销。
3. 分别构造只丢SEI、只丢画面／分片、呈现丢弃及服务器剥离SEI，验证不会误报帧丢失；验证SEI路径失效时普通素材主方案仍可工作。
4. 比较两种帧身份路径及延迟结果，并解释共同的时钟／呈现误差。音画同步仍独立核对音频设备消费，不能只比两个时间戳字段。
5. 只有本机协议矩阵与异常路径通过后，才考虑纳入可选诊断；若要改为主方案，需要明确变更M-03／M-09／L-04基线及外部无标记源的支持边界。

基础当前范围与待验收项见[需求追踪](./需求追踪与验收状态.md)，本评估不再维护早期阶段工作编号。尚未授权直接将SEI变成正式检测前提，本轮不更改主算法或媒体。
