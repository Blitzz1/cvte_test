# 预览与接收计时核对记录

日期：2026-10-29。本轮只运行限时测试，结束后均清理检测程序及 MediaMTX。用户的 app.json、single-chain.json 修改和未知临时文件保持原状。

## 1. 修复与测量边界

### WIC 预览

原实现把整个 WIC 布局分区复制成 JPEG。例如两路时分区为500×600，而16:9画面仅占500×281，网页再套固定280px高度，产生内外两层留黑。

现在绘制与镜像共用同一个整数内容矩形，只复制实际绘制区域；单路使用完整1000px宽的输出目标，实测 JPEG 为1000×563。网页图像宽度占满容器、高度按图像比例自适应，保留原始画面内容，不拉伸、不裁切素材自带黑边。多路仍复用现有 WIC 合成目标，各页面只显示本路内容；未增加拉流或解码，仍最多10Hz的实际像素镜像。此项改变预览布局，不把浏览器JPEG显示时间纳入主呈现时间。

真实输出图、HTTP帧ID／代次／观测时间头保存在 [证据目录](./evidence/2026-10-29/preview-and-timing/)。本轮已核验实际JPEG和前端尺寸规则；限时运行结束后浏览器自动化连接被拒，未取得本轮网页实况截图，因此不宣称完成Chrome／Edge现场视觉验收。

### 接收与身份关联

检查确认：接收线程原本就把 `now_us()` 放在 `av_read_frame` 成功返回后的第一条语句，早于哈希、链路互斥锁、源端对象查找。`transport_ms = received_us - source_us`，未把这些接收后操作误算进传输段；本轮保留这一正确边界。

接收点是**完整压缩帧从解封装接口返回**，不是网卡／操作系统收到最后一个UDP或TCP包。它包括发送与服务器等待、接收解封装、组帧及接口内部缓冲；不能把它称为纯网络传输时间。文件源的source_us是按DTS实时调度后、源端签名准备完成并释放帧进行发送的时刻，既不是素材拍摄时间，也不是文件PTS对应的墙钟。完整端到端 `latency_ms` 仍到WIC绘制完成，现有告警沿用该口径。

新增逐帧原始 `receiver_association`，记录接收、哈希开始／结束、请求锁／取得锁、匹配开始／完成七个单调时刻。归因区新增近1秒同组样本的哈希、锁等待、匹配及匹配事件记录、其他记账、关联总耗时；四个子项严格相加为关联总耗时。关联完成后到送入解码前仍有故障判断和提交准备，不能将关联总耗时冒充整个接收后准备段。完整六时刻分段继续独立保留，两个样本集合不保证相同。

新增 `publish_write` 记录源端释放、调用发送接口前／后的时间。发送函数返回不代表远端收到，也不能据此扣除所有发送缓冲。签名规范化向量预留容量，减少反复扩容，保持匹配算法及媒体内容不变。

UDP中继在 `recvfrom` 返回后立即记录时间，帧末marker事实携带 `last_packet_us`。时间戳切换／结束冲刷时 `marker_seen=false`，不能把这种不完整边界混作帧末证据。marker加旁路签名唯一匹配只是本机中继观测，不能代表网卡到达；TCP与RTMP没有伪造同等网络包时间。

## 2. RTSP 与 RTMP 的实测差异

同一1080p30 H.264／AAC素材，三条独立本机完整链路并行、无故障注入，90秒硬截止；去除开始15秒预热后，逐帧核对如下。单位ms。

| 实测阶段均值 | RTSP UDP | RTSP TCP | RTMP |
|---|---:|---:|---:|
| 源端释放→完整压缩帧返回 | 45.438 | 45.478 | 11.967 |
| 接收后哈希 | 0.094 | 0.109 | 0.098 |
| 接收后等待锁 | 0.0003 | 0.0004 | 0.0007 |
| 身份匹配及匹配记录 | 0.029 | 0.032 | 0.032 |
| 接收→关联完成 | 0.124 | 0.143 | 0.131 |
| 源端释放→发送接口调用 | 0.046 | 0.037 | 0.036 |
| 发送接口调用 | 0.209 | 0.205 | 0.262 |
| 源端释放→UDP中继帧末包 | 13.197 | 无该观测 | 无该观测 |
| UDP中继帧末包→完整压缩帧返回 | 32.241 | 无该观测 | 无该观测 |

UDP同帧2245组可直接拆分：13.197 + 32.241 = 45.438。30fps一帧约33.333ms；RTSP TCP、UDP相差很小，且它们在下一视频源帧释放后约12.1ms返回上一帧，RTMP同帧约12.0ms即可返回。接收后哈希／锁并非这33ms差距的原因，发送调用耗时也解释不了它。

FFmpeg 8.1 的 [H.264 RTP处理器](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavformat/rtpdec_h264.c)设置 `AVSTREAM_PARSE_FULL`；[H.264解析器](https://github.com/FFmpeg/FFmpeg/blob/n8.1/libavcodec/h264_parser.c)根据后续NAL／下一图像边界确定上一帧结束，无完整边界时继续合并等待。实测和源码共同支持：**本项目当前素材、FFmpeg接收路径存在约一帧的解析／组帧等待，是差值的主要解释**。UDP帧末到接口返回还包含中继转发、线程调度、socket／解封装等开销，未给FFmpeg内部函数单独插桩，不将32.241ms全部声称为纯解析器CPU耗时。TCP没有同位置逐包打点，对它的解析归因为源码与同帧时序支持的判断，而非已独立测出全部内部耗时。

该差异并非证明RTSP协议必然比RTMP慢，也非证明RTMP网络仅需12ms。没有从结果中人为扣除一帧、取消必要解析或更改素材编码来制造更低指标。当前数值在已声明的软件接口边界下合理；未来若需要纯网络／socket到达口径，必须为各协议另建一致且可关联的更底层观测点。
